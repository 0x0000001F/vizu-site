# Module 3 · ARM64

Read alongside: Arm, *Learn the architecture: A64 Instruction Set
Architecture* (free guide) · Pyeatt and Ughetta, *ARM 64-Bit Assembly
Language*

ARM64 (AArch64) runs phones, tablets, Apple's M chips and a growing share of
servers. It is a RISC design: every instruction is 4 bytes, arithmetic
works only on registers, and only loads and stores touch memory. Programs
use GNU as syntax: the destination first, a `#` before numbers, `//` for
comments.

## 3.1 Registers: x0–x30, w, sp and xzr

**Read:** A64 guide, "Registers" · Pyeatt, the register chapter
**You will:** use the 31 registers, their 32-bit halves, and the zero
register.

There are 31 registers of 64 bits, `x0` to `x30`; `w0` to `w30` are their
low 32 bits (and writing a `w` register clears the top half, as on
x86-64). `x30` is the *link register*, where `bl` leaves the return address;
`x29` is the frame pointer by convention. `sp` is separate, and register
number 31 means `sp` in some instructions and **`xzr`**, the zero register,
in others: it reads as 0, and what is written to it is thrown away.

An instruction has room for only 16 bits of a number, so a bigger one is
built in pieces with `movz` and `movk`.

```asm run arch="arm"
    .text
    .global _start
_start:
    mov  x0, #-1            // all 64 bits set (it becomes movn)
    mov  w0, #5             // writing w0 clears the top half: x0 = 5
    mov  x1, #0x1234
    movk x1, #0xabcd, lsl #16   // 16 more bits above: x1 = 0xabcd1234
    add  x2, xzr, x1        // xzr reads as 0, so x2 = x1
    mov  x8, #93
    svc  #0                 // exit(x0): 5
```

**Watch:**

- `mov` is a pseudo-instruction: the decoder sees `movn`, `movz` or `orr`,
  depending on the number.
- `movk` keeps the other bits and replaces 16 of them: `x1` goes from
  `0x1234` to `0xabcd1234`.
- In the decoder, `Rn` = `11111` for `xzr`, and the register file has no
  box for it: it is not a register, just a 0.

### Check yourself

1. Why does `mov x0, #100000` fail?
   <details><summary>Answer</summary>

   100000 needs 17 bits. Write `movz x0, #0x86a0` then `movk x0, #1, lsl
   #16` (0x186a0 = 100000).
   </details>

2. What is in `x0` after `mov w0, #5`, if it held −1 before?
   <details><summary>Answer</summary>

   5: writing a `w` register clears the upper 32 bits of the `x` register.
   </details>

### Common mistake

Mixing `x` and `w` registers in one instruction (`add x0, x1, w2`): each
instruction works at one width, and the assembler refuses.

## 3.2 Arithmetic: three registers, flags only when asked

**Read:** A64 guide, "Data processing" · Pyeatt, the data processing chapter
**You will:** compute with three operands and set flags on purpose.

ARM64 arithmetic names three registers: `sub x2, x0, x1` is `x2 = x0 −
x1`, and the sources stay as they were. Flags (N, Z, C, V) change **only**
in instructions ending in **s**: `adds`, `subs`, and `cmp` (a `subs` into
`xzr`). There is no remainder instruction: `udiv` divides, and `msub`
computes `a − b × c`, which gives the remainder.

```asm run arch="arm"
    .text
    .global _start
_start:
    mov  x0, #7
    mov  x1, #10
    sub  x2, x0, x1         // -3, the flags do not change
    subs x3, x0, x1         // -3 again, and N Z C V are set
    mov  x4, #100
    mov  x5, #7
    udiv x6, x4, x5         // 14
    msub x7, x6, x5, x4     // 100 - 14 * 7 = 2: the remainder
    mov  x0, x7
    mov  x8, #93
    svc  #0                 // exit(2)
```

**Watch:**

- `sub` leaves the flags alone; `subs` sets N = 1 (negative) and C = 0. On
  ARM, C after a subtraction means *no borrow*, the opposite of x86's CF.
- `udiv` drops the remainder; `msub` gets it back.
- Dividing by zero does not trap on ARM64: `udiv` gives 0.

### Check yourself

1. What are N, Z, C and V after `subs x3, x0, x1` (7 − 10)?
   <details><summary>Answer</summary>

   N = 1 (−3 is negative), Z = 0, C = 0 (there was a borrow: as unsigned,
   7 < 10), V = 0 (no signed overflow).
   </details>

2. How would you compute `x0 % 8` without dividing?
   <details><summary>Answer</summary>

   For unsigned numbers, keep the low 3 bits: an `and` with 7 (put 7 in a
   register first; this course leaves out ARM's bitmask immediates).
   </details>

### Common mistake

Writing `sub` before a conditional branch and expecting it to set the
flags. Only `subs`, `adds`, `cmp`, `cmn`, `tst` and `ands` do.

## 3.3 Branches

**Read:** A64 guide, "Program flow" · Pyeatt, the branch chapter
**You will:** loop with `b.cond`, and with `cbnz`, which needs no flags.

`b label` always branches; `b.eq`, `b.ne`, `b.lt`, `b.le`, `b.gt`, `b.ge`
(and the unsigned `b.lo`, `b.hs`, `b.hi`, `b.ls`) branch on the flags. Two
branches compare with zero by themselves: `cbz` (branch if zero) and `cbnz`
(if not zero).

```asm run arch="arm"
    .text
    .global _start
_start:
    mov  x0, #0             // sum
    mov  x1, #1             // i
again:
    add  x0, x0, x1         // sum += i
    add  x1, x1, #1         // i++
    cmp  x1, #5
    b.le again              // while i <= 5
    mov  x2, #3
down:
    sub  x2, x2, #1
    cbnz x2, down           // no cmp: it compares with 0 itself
    mov  x8, #93
    svc  #0                 // exit(15)
```

**Watch:**

- `cmp x1, #5` is `subs xzr, x1, #5`: the result is thrown away, the flags
  stay.
- `b.le` reads Z, N and V; the decoder shows its condition field, `1101`.
- `cbnz x2, down` reads `x2` in Decode and decides in Execute, with no
  flags at all.

### Check yourself

1. How far can `b.le` jump?
   <details><summary>Answer</summary>

   Its offset is 19 bits, counted in instructions: about ±1 MiB. `b` has 26
   bits: ±128 MiB.
   </details>

2. Why is `cbnz` handy in a countdown?
   <details><summary>Answer</summary>

   It saves the `cmp`: one instruction tests and branches.
   </details>

### Common mistake

Using `b.lt` and `b.gt` for unsigned values (addresses, sizes): use `b.lo`
and `b.hi` instead, which read C.

## 3.4 Load and store

**Read:** A64 guide, "Loads and stores" · Pyeatt, the load/store chapter
**You will:** read a string byte by byte with post-indexing.

Only `ldr` and `str` (and `ldrb`/`strb` for bytes, `ldp`/`stp` for pairs)
touch memory. The address is a register plus an offset: `[x1, #8]`.
**Pre-index** `[x1, #8]!` adds first and keeps the new address in `x1`;
**post-index** `[x1], #1` uses `x1` and then adds, perfect for walking
through memory. `adr x1, label` puts a nearby label's address in a register,
counted from the PC.

```asm run arch="arm"
    .data
s:  .asciz "assembly"
    .text
    .global _start
_start:
    adr  x1, s              // x1 = the string's address
    mov  x0, #0             // count
next:
    ldrb w2, [x1], #1       // load a byte, then x1 += 1
    cbz  w2, done           // the 0 at the end
    add  x0, x0, #1
    b    next
done:
    mov  x8, #93
    svc  #0                 // exit(8)
```

**Watch:**

- `ldrb w2, [x1], #1`: Execute uses `x1` as the address and also computes
  `x1 + 1`; Write back updates both `w2` and `x1`.
- A byte loads into a `w` register, zero-extended.
- `adr x1, s` is one instruction: the PC plus a 21-bit offset.

### Check yourself

1. What is the difference between `ldr x0, [x1, #8]!` and `ldr x0, [x1],
   #8`?
   <details><summary>Answer</summary>

   The first reads at `x1 + 8` and sets `x1 = x1 + 8`; the second reads at
   `x1` and then sets `x1 = x1 + 8`.
   </details>

2. Why can ARM64 not add a memory value to a register in one instruction?
   <details><summary>Answer</summary>

   It is a load/store architecture: arithmetic takes registers only. It
   keeps the instructions simple and the same size; the load comes first.
   </details>

### Common mistake

`ldr x0, [x1]` where `x1` holds a value instead of an address: the CPU reads
whatever address that number is, and the kernel stops the program with a
segmentation fault.

## 3.5 Functions: bl, x30 and the frame

**Read:** A64 guide, "Function calls" · Pyeatt, the subroutine chapter
**You will:** call a function that calls another, and save x30.

`bl label` puts the return address in `x30` and branches; `ret` branches to
`x30`. Nothing is pushed, so a function that calls another must save `x30`
first, usually with `x29` as a pair: `stp x29, x30, [sp, #-16]!` on the way
in, `ldp x29, x30, [sp], #16` on the way out. The ARM calling convention
(AAPCS64) passes arguments in `x0`–`x7` and returns in `x0`; `x19`–`x28`
must be given back unchanged. `sp` must stay a multiple of 16.

```asm run arch="arm"
    .text
    .global _start
_start:
    mov  x0, #3
    bl   cube               // x30 = the next address
    mov  x8, #93
    svc  #0                 // exit(27)

cube:                       // long cube(long n)
    stp  x29, x30, [sp, #-16]!   // save the frame pointer and x30
    mov  x29, sp
    str  x0, [sp, #-16]!    // keep n (16 bytes, to keep sp aligned)
    bl   square             // x0 = n * n, and x30 changes!
    ldr  x1, [sp], #16      // n back
    mul  x0, x0, x1         // n * n * n
    ldp  x29, x30, [sp], #16     // x30 is the return address again
    ret

square:
    mul  x0, x0, x0
    ret                     // back to x30
```

**Watch:**

- `bl cube`: Write back puts `0x1008` in `x30`.
- `stp` writes 16 bytes on the stack in one go; `bl square` then replaces
  `x30`, and only the saved copy gets `cube` home.
- `ldp x29, x30, [sp], #16` reloads both and moves `sp` back up.

### Check yourself

1. What goes wrong if `cube` does not save `x30`?
   <details><summary>Answer</summary>

   `bl square` overwrites it; `cube`'s `ret` then returns into itself,
   right after `bl square`, and loops or crashes.
   </details>

2. Why does `str x0, [sp, #-16]!` move `sp` by 16 for 8 bytes?
   <details><summary>Answer</summary>

   ARM64 requires `sp` to be a multiple of 16 when it is used for memory;
   Linux turns a misaligned access into a SIGBUS.
   </details>

### Common mistake

Moving `sp` by 8. The next access through `sp` faults:

```asm run arch="arm" expect="error"
    .text
    .global _start
_start:
    mov  x0, #1
    str  x0, [sp, #-8]!     // sp = 0x7ff8: not a multiple of 16
    ldr  x1, [sp]           // an access through sp: alignment fault
    mov  x8, #93
    svc  #0
```

## 3.6 System calls

**Read:** A64 guide, "Exceptions" · Linux's `asm-generic/unistd.h`
**You will:** print with `svc #0`.

`svc #0` raises an exception from EL0, where programs run, to EL1, where the
kernel runs. Linux on ARM64 takes the call's number in `x8` and arguments in
`x0`–`x5`; it returns in `x0`. The numbers are the generic Linux ones,
shared with RISC-V: 63 `read`, 64 `write`, 93 `exit`.

```asm run arch="arm"
    .data
msg:    .ascii "Hello, ARM\n"
    .equ len, . - msg
    .text
    .global _start
_start:
    mov  x0, #1             // fd 1: stdout
    adr  x1, msg
    mov  x2, #len
    mov  x8, #64            // 64: write
    svc  #0
    mov  x0, #0
    mov  x8, #93            // 93: exit
    svc  #0
```

**Watch:**

- The CPU badge says *kernel mode* in the Kernel stage: the exception
  handler runs the kernel's `write`.
- `x0` comes back as 11, the bytes written.
- The `svc` number (`#0`) is ignored by Linux; `x8` says what to do.

### Check yourself

1. Which register holds the system call's number on ARM64, and on x86-64?
   <details><summary>Answer</summary>

   `x8` on ARM64, `rax` on x86-64 (and `a7` on RISC-V).
   </details>

2. Why are the numbers different on x86-64?
   <details><summary>Answer</summary>

   x86-64 Linux kept its own table from its start; ARM64 and RISC-V came
   later and use the generic one.
   </details>

### Common mistake

Copying an x86-64 number (`write` = 1) into an ARM64 program: 1 is not
`write` here, and the kernel answers with an error code instead of output.
